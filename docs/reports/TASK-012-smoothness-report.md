# TASK-012 报告：消除切换闪烁（「频繁闪闪闪，而不是平滑的播放」）

> 触发：用户反馈「所产出视频，频繁闪闪闪的，而不是平滑的播放」。
> 本文沿用 TASK-011 的方法：**不凭观感下结论，先量化，再定位到行**。
> 判断对象仍是 `.out/demo.mp4`（`b4f64e4` 的产物）。修复后另出一版对照。

---

## 0. 结论摘要

**症状是真的，而且完全可量化：98 秒里画面真正"动"的只有 115 帧（3.9%）。**
其余 96% 的帧**逐帧完全静止**（1760 帧的帧间差精确等于 0）。用户的"闪"不是错觉，
是 **9 次**（8 个节点切换 + 1 次片尾）**突变点在 96% 的静止背景上被放大**的结果。

**根因不是渲染、不是编码，是"切换时一瞬间翻转了四件事 + 相机匀速猛冲猛停"。**
全部落在渲染层的三个文件里，与管线无关。

| 维度 | 判定 |
|---|---|
| 是否真 bug | ✅ 是。opacity / 边框色 / 圆点尺寸在**单帧内**跳变，相机是**纯线性匀速** |
| 是否编码问题 | ❌ **不是**。`imageFormat: 'jpeg'` 曾被怀疑，数据已排除（§4） |
| 是否管线问题 | ❌ 不是。渲染与封装本身无缺陷 |
| 修复面 | 4 个文件 + 1 个新工具 + 11 个新测试用例 |

**修复后**（实测于 `.out/demo-smooth.mp4`，见 §6.4）：

- 切换的**起步帧帧差从 3.14095 降到 0.07067**（**44.4 倍**）—— 垂直跳变消失
- 帧差序列由 `0 → 3.14 → 2.5×15 → 0`（方波）变为 `0 → 0.07 → … → 2.69 → … → 0.07 → 0`（山丘）
- opacity 的单帧变化从 **0.6000 降到 0.0689**（8.7 倍）
- 相机的速度曲线从「0 → 16.76 → 0 px/帧 的方波」变成「0 → 峰 28.88 → 0 的山丘」，
  起步与刹车不再有硬边

## 1. 量化方法：帧间差分

观感无法验收，但"每一帧相对前一帧变了多少"可以。用 FFmpeg 的
`tblend=difference`（逐像素取绝对差）+ `signalstats` 取该差分图的平均亮度 `YAVG`
作为**帧间变化量**，得到一条 2941 个样本的序列。

```bash
FF="/Applications/微信秒剪特效.app/Contents/bin/ffmpeg/x86_64"
"$FF/ffmpeg" -v error -i .out/demo.mp4 \
  -vf "tblend=all_mode=difference,signalstats,metadata=print:key=lavfi.signalstats.YAVG:file=/tmp/fdiff.txt" \
  -f null -
```

## 2. 数据：96% 静止 + 9 个突变点

### 2.1 帧变化的分布

| 变化量 | 帧数 | 占比 | 含义 |
|---|---|---|---|
| **恰好 0** | 1760 | **59.8%** | 逐帧完全静止 —— 一个像素都没动 |
| < 0.001 | 1049 | 35.7% | 近静止 |
| 0.001 – 0.05 | 8 | 0.3% | 可忽略 |
| ≥ 0.5 | **115** | **3.9%** | 大幅运动 |

**96% 的画面时间是"死"的。** 这本身就是 TASK-011 里"每屏静置 12.03 秒"的机械证据，
但它同时解释了"闪"为什么刺眼：**在一条几乎水平的基线上，任何突变都格外突出。**

### 2.3 单次切换的逐帧形态（帧 1471–1497）


## 3. 根因：一次切换同时翻转四件事 + 匀速猛冲

### 3.1 透明度在单帧内跳变 0.6

`packages/layouts/src/timeline.ts:92` 是一个**阶梯函数**，没有中间值：

```ts
const opacity = inIntro || inOutro ? 0.5 : node.id === activeNodeId ? 1.0 : 0.4;
```

而 `camera.ts`（TASK-007 版）的文档明说**它不插值 opacity**：

> Only `items[].x` and `timeline.x0/x1` are interpolated; `y`, `opacity` and `visible`
> are taken verbatim from `currentLayout` (per the contract).

于是每 12 秒有一次：**两张卡同时在一帧内完成 1.0 ↔ 0.4 的翻转**。
实测这个瞬间就是全片最大的帧差（3.14）。

### 3.2 边框颜色在单帧内跳变

`packages/kit/src/EventCard.tsx`：

```ts
const borderColor = featured ? tokens.color.accent
  : active ? tokens.color.foreground      // #e8eaf0 亮白
           : tokens.color.timelineLine;    // #2a3144 暗蓝
```

布尔量驱动 → 上交棒的卡"白框"瞬间熄灭，接棒的卡"白框"瞬间点亮。
**深底上一圈 2px 的白框出现/消失，本身就是一记可见的闪。**

### 3.3 圆点在一帧内同时改变尺寸、颜色、光晕

`packages/kit/src/Timeline.tsx`：

```ts
const dotColor = node.active || node.featured ? tokens.color.accent : tokens.color.muted;
const size = node.active || node.featured ? 18 : 12;
boxShadow: node.active ? `0 0 16px ${tokens.color.accent}` : 'none',
```

12→18px、灰→金、无光晕→有光晕，**三件事都在同一帧完成**。

### 3.4 相机是纯线性插值，等价于"速度方波"

`packages/compositions/src/camera.ts`：

```ts
const t = Math.min(framesSinceSwitch / transitionFrames, 1);
... x: lerp(previousX, item.x, t)
```

线性 ⇒ 每帧位移相同 ⇒ **速度在第 1 帧从 0 突跳到 16.76 px/帧，在第 15 帧又突跳回 0**。
`camera.ts` 的文件头注释写着 "TASK-007 smooths the motion via Remotion springs/interpolate"，
但实现里既没有 spring 也没有 easing —— **注释与实现不符**。

### 3.5 过渡本身太短

`TRANSITION_FRAMES = 15`（0.5 秒）要吃掉 251.43 px：

```
251.43 px / 15 帧 = 16.76 px/帧 ≈ 503 px/s
```

30 fps 下每帧跳 16.76 px（占屏宽 0.87%），在**没有运动模糊**的逐帧渲染里会被看成"台阶"。

### 3.6 汇总：一次切换 = 四重硬跳 + 一段方波运动

```
帧 1476 这一帧上同时发生：
  ① 两张卡的 opacity 互翻 1.0 ↔ 0.4
  ② 两张卡的边框色 亮白 ↔ 暗蓝
  ③ 两个圆点 18px ↔ 12px
  ④ 一个圆点的光晕 出现 / 消失
之后 15 帧：画面以恒定 16.76 px/帧 平移，然后骤停。
```

**这就是"闪闪闪"的完整机制。** 9 次，每 12 秒一次。

## 4. 排除的嫌疑：JPEG 不是元凶

初查时 `render.ts:207` 的 `imageFormat: 'jpeg'` 是头号嫌疑 ——
深色背景 + 细白字 + 4px 细线正是 JPEG 块效应与蚊噪最严重的内容，
而"二次压缩导致画面沸腾"是已知的伪影来源。

**数据把它排除了**：**1760 帧的帧间差精确等于 0**。

如果 JPEG 的块效应在逐帧之间发生跳变，静止段必然出现非零噪声。实际是**精确的 0**，
说明编码是**确定性**的，没有"沸腾"。

> JPEG 仍然降低单帧画质（块效应、色度子采样）—— 记为待办，但它**不产生闪烁**。
> 这一点必须写清楚，避免下次误诊。

## 5. 修复

改动全部在**渲染层**，不动布局层（ADR-004：布局层给确定性目标，渲染层负责平滑）。

| # | 文件 | 改动 |
|---|---|---|
| 1 | `compositions/src/camera.ts` | 新增 `easeInOutCubic`；相机的 x **和** opacity 都走这条曲线 |
| 2 | `compositions/src/camera.ts` | **插值 opacity**（TASK-007 版是 verbatim 取值 → 硬跳的直接原因） |
| 3 | `compositions/src/TimelineComposition.tsx` | `TRANSITION_FRAMES` 15 → **24**（0.5s → 0.8s） |
| 4 | `compositions/src/TimelineComposition.tsx` | 引入 `activeAmount ∈ [0,1]` 取代布尔 `active`，**与相机的 opacity 共用同一条缓动曲线** |
| 5 | `kit/src/EventCard.tsx` | `active?: boolean` → `activeAmount?: number`，边框色走 `interpolateColor` |
| 6 | `kit/src/Timeline.tsx` | 圆点的尺寸 / 颜色 / 光晕全部由 `activeAmount` 连续驱动 |
| 7 | `kit/src/color.ts`（新） | `interpolateColor`：Remotion 每帧独立截图，CSS `transition` 永不运行，任何随时间变化的值都必须由每帧的数字驱动 |
| 8 | `compositions/src/TimelineComposition.tsx` | `scale` 从布尔（`isActive ? 1 : fitScale`）改为连续量 —— **这是第一轮修复的遗漏**，只有重渲染后量数据才暴露，见 §6.4 |

### 5.1 关键设计：一条曲线驱动全部

`activeAmount` 的取法（`TimelineComposition.tsx`）：

```ts
const transitionProgress = easeInOutCubic(Math.min(framesSinceSwitch / TRANSITION_FRAMES, 1));
const activeAmountOf = (id: string): number => {
  const wasActive = id === previousActiveId;
  const isActive = id === currentLayout.activeNodeId;
  if (isActive && wasActive) return 1;
  if (isActive) return transitionProgress;      // 0 → 1 淡入
  if (wasActive) return 1 - transitionProgress; // 1 → 0 淡出
  return 0;
};
```

**它与 `smoothCamera` 里的 opacity 用的是同一条 `easeInOutCubic`** —— 这是"卡片亮起来"
和"卡片滑到位"读起来像**一个动作**、而不是两段各走各的动画的原因。

### 5.2 修复前后的运动学

| | 修复前 | 修复后 |
|---|---|---|
| 过渡时长 | 15 帧（0.50 s） | 24 帧（0.80 s） |
| 相机速度曲线 | **方波**：0 → 16.76 → 0 px/帧 | **山丘**：0 → 峰 28.88 → 0 px/帧 |
| 首帧位移 | 16.76 px（瞬间满速） | **0.073 px**（几乎不动） |
| opacity 单帧最大变化 | **0.6000**（硬跳） | **0.0689** |
| 边框色 / 圆点 | 单帧硬跳 | 与 opacity 同步过渡 |

> 峰值速度从 16.76 升到 28.88 px/帧：这是 S 曲线的固有代价——同样的位移用更长时间
> 完成，中间段必然更快。**换来的是两端不再有速度突变**，而人眼对"速度突变"的敏感度
> 远高于对"匀速偏高"的敏感度。若观感仍嫌快，调大 `TRANSITION_FRAMES` 即可线性降低峰值
> （峰值 ≈ `251.43 × 3 / TRANSITION_FRAMES`，取 45 帧时回到 16.76）。

### 5.3 新增测试（11 个用例）

### 6.3 一个分析要点：帧差**不是**平滑度指标

必须写清楚，否则会误判：

- **帧差（一阶）**衡量"这一帧变了多少" → 匀速高速运动也会产生**大而恒定**的帧差
- **平滑度（二阶）**取决于"帧差本身是否连续变化"

修复后，切换点的帧差**峰值未必下降**（S 曲线的中间段更快）。真正的判据是
**帧差序列的形状**：从"垂直上、平台、垂直下"变成"缓升、峰、缓降"。
因此 §6.4 既给数值，也给序列本身。

### 6.5 一个反复踩到的环境坑（非代码问题）

第一轮渲染**失败**在：

```
✖ Timed out after 25000 ms while trying to connect to the browser! Chrome logged the following:
```

（注意冒号后是**空的** —— Chrome 一行日志都没来得及输出。）

这不是代码问题，是**那堵硬编码的 25 s 墙**（见 skill `remotion-render-diagnostics` §3.1）。
触发条件是两个叠加：① 跑渲染前刚跑完 vitest / tsc，Chrome 冷启动抢不到 CPU；
② 上一次失败留下了 5 个孤儿 `puppeteer_dev_chrome_profile-*` 进程，**内存只剩 15 MB 空闲**。

处置（实测有效）：

```bash
pgrep -f "puppeteer_dev_chrome_profile" | xargs -n1 kill -9
rm -rf /var/folders/*/*/T/puppeteer_dev_chrome_profile-*
cat "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    "/Applications/Google Chrome.app/Contents/Frameworks/Google Chrome Framework.framework/Versions/<版本>/Google Chrome Framework" > /dev/null
```

清理后空闲内存 15 MB → 355 MB（51952 页），两轮渲染分别 591 s / 417 s 全部通过。

> **教训**：验证链（lint/typecheck/test）与渲染**不要串在同一个进程里紧接着跑** ——
> 中间要留回收时间，并先清孤儿 Chrome。这条已补进 skill 的自检清单。
